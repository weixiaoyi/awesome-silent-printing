# Web からのバッチ・ラベル印刷

## 課題

倉庫や EC デスクでは、人が印刷ダイアログをクリックし続けずに**数十〜数百枚**のラベルが必要なことが多いです。ラベル 1 枚ごとにダイアログ 1 回は運用設計ではなく、障害です。

## 必要なもの

1. **名前指定**プリンターへのサイレント経路
2. ジョブキュー / バッチ API（大規模ではクライアント側ループだけでは不足）
3. 安定したテンプレートレンダリング（HTML または ZPL）
4. バッチ途中失敗時のリトライ + ログ
5. プリンターが送信側より遅い場合のバックプレッシャー

## パターン

| パターン | 備考 | 最適な場合 |
|---|---|---|
| ブラウザ → ローカルエージェントバッチ API | デスク PC で最低レイテンシ | オペレーターが SPA 内で作業 |
| サーバー push → デスクエージェント pull | 多数の梱包ステーション向け | ブラウザを開いたままにすべきでない |
| ベンダー raw（ZPL） | 純ラベルプリンターに最適 | 端末群がすでに ZPL に標準化 |

## 推奨バッチフロー

```text
Select orders
  → render or fetch N templates
  → submit as a batch (or chunked batches of 20–50)
  → show per-job status (queued / printing / done / failed)
  → retry failed ids only
```

### チャンク分割

500 ジョブを 1 つの Promise.all で送ると、助けになるより害になることが多い。チャンクを推奨：

- HTML レンダリングエージェントは 20〜50 ジョブ / チャンク
- 小さな ZPL 文字列ならより大きなチャンクも可
- 次のチャンク前にチャンク完了を待つ（または同時実行上限 2〜3）

## 失敗の分類

| 失敗 | オペレーター対応 | システム対応 |
|---|---|---|
| エージェントオフライン | インストール / 起動 | キュー一時停止；バナー |
| プリンターオフライン / 用紙切れ | ハードウェア修正 | ジョブをリトライ可能にマーク |
| 不良テンプレート / バーコード | データ修正 | そのジョブのみ失敗；他は継続 |
| LNA / HTTPS | IT がオリジン修正 | [Chrome LNA](chrome-local-network-access.ja.md) を参照 |

## チェックリスト

- [ ] 用紙サイズ / ステーションごとのプリンター選択
- [ ] バッチ送信 + ジョブごとのステータス
- [ ] HTTPS ページが localhost に到達可能（LNA）
- [ ] バーコード / QR のテンプレート回帰テスト
- [ ] 冪等 job id（再送信安全）
- [ ] 運用が失敗 job id をエクスポート可能
