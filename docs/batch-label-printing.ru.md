# Пакетная печать и этикетки из веба

## Проблема

На складах и в ecommerce часто нужны **десятки или сотни** этикеток без кликов по диалогам печати. Один диалог на этикетку — не операционный дизайн, а сбой.

## Что нужно

1. Тихий путь к **именованному** принтеру
2. Очередь / batch API (клиентский цикл недостаточен в масштабе)
3. Стабильный рендер шаблона (HTML или ZPL)
4. Retry + логирование при сбое посередине пакета
5. Back-pressure, когда принтер медленнее отправителя

## Паттерны

| Паттерн | Заметки | Лучше когда |
|---|---|---|
| Браузер → batch API локального агента | Минимальная задержка на рабочем ПК | Оператор работает в SPA |
| Push сервера → pull агента на столе | Лучше для многих упаковочных станций | Браузер не должен быть открыт |
| Vendor raw (ZPL) | Отлично для чистых этикеточных принтеров | Парк уже на ZPL |

## Рекомендуемый поток пакета

```text
Выбор заказов
  → рендер или загрузка N шаблонов
  → отправка пакетом (или чанками по 20–50)
  → статус по каждому заданию (queued / printing / done / failed)
  → retry только failed id
```

### Чанкирование

500 заданий в одном Promise.all часто вредит больше, чем помогает. Лучше чанки:

- 20–50 заданий на чанк для HTML-агентов
- Большие чанки могут подойти для крошечных ZPL-строк
- Дождитесь завершения чанка (или limit concurrency 2–3) перед следующим

## Таксономия сбоев

| Сбой | Действие оператора | Действие системы |
|---|---|---|
| Агент offline | Установить / запустить агент | Пауза очереди; баннер |
| Принтер offline / нет бумаги | Починить железо | Пометить retryable |
| Плохой шаблон / штрихкод | Исправить данные | Fail этого задания; остальные продолжают |
| LNA / HTTPS | IT чинит origin | См. [Chrome LNA](chrome-local-network-access.ru.md) |
