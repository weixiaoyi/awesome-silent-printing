# 사일런트 프린트 동작 원리

브라우저는 웹페이지가 조용히 물리 프린터로 작업을 보내는 것을 **막도록** 설계되어 있습니다. 그래서 `window.print()`는 대화상자를 띄우고, "순수 JavaScript로 사일런트 프린트"는 보통 막다른 길입니다.

웹 앱에서 영수증, 배송 라벨, 청구서, 주방 티켓을 만들고 있다면 브라우저 플래그가 아니라 다른 아키텍처가 필요합니다.

## 실제 패턴

프로덕션 사일런트 프린트 설정은 거의 모두 이렇게 생겼습니다.

```text
Web app (browser)
    → localhost HTTP / WebSocket / Native Messaging
    → local agent / vendor service / desktop shell
    → OS print spooler or raw device port
```

페이지가 프린터를 소유하지 않습니다. **신뢰할 수 있는 로컬 컴포넌트**가 소유합니다. 이 컴포넌트는 워크스테이션마다(또는 키오스크 이미지에 포함되어) 한 번 설치되고, 웹 앱은 로컬 서비스로 대화합니다.

### 왜 이렇게 되어 있을까

| 관심사 | 브라우저의 답 | 사일런트 프린트의 답 |
|---|---|---|
| 악성 사이트의 스팸 인쇄 | 조용한 장치 접근 차단 | 사용자가 알려진 에이전트 설치 |
| 잘못된 프린터 선택 | 대화상자 강제 | 에이전트 + 이름 지정 프린터 API |
| Raw ESC/POS / ZPL | 페이지에서 불가 | 에이전트 또는 벤더 SDK가 바이트 전송 |
| 배치 / 무인 작업 | 대화상자가 흐름을 끊음 | 에이전트 또는 서버에서 큐 |

## 다섯 가지 아키텍처

| 접근 방식 | 누가 무엇을 설치하는가 | 일반적 용도 | 트레이드오프 |
|---|---|---|---|
| 로컬 프린트 브리지 | 데스크톱 에이전트 + JS SDK | ERP, WMS, POS, 라벨 | 웹 사일런트 프린트에 가장 일반적 |
| 확장 프로그램 + 네이티브 호스트 | 브라우저 확장 + 호스트 앱 | 잠긴 플릿 | 스토어 심사 + 신뢰 마찰 |
| 엔터프라이즈 / 키오스크 정책 | 관리형 브라우저 이미지 | 키오스크 전용 | 공개 SaaS 사용자에게는 부적합 |
| 하드웨어 벤더 SDK | 벤더 서비스 또는 네트워크 프린터 API | Zebra / Epson / Star 플릿 | 하드웨어 종속 |
| 데스크톱 셸 (Electron…) | 자체 데스크톱 앱 | 클라이언트를 통제할 때 | 순수 브라우저 앱은 아님 |

인터넷의 "Chrome에서 사일런트 프린트" 스레드는 결국 **로컬 프린트 브리지** 또는 **벤더 SDK**로 수렴하는 경우가 많습니다.

## 한 번의 인쇄 작업에서 일어나는 일

일반적인 HTML/PDF 브리지 작업:

1. SPA가 HTML(또는 PDF URL / 바이트)을 만듭니다.
2. SDK가 `https://yoursite` → `ws://127.0.0.1:port`(또는 HTTP)를 엽니다.
3. 에이전트가 작업을 받아, 필요하면 내장 Chromium에서 HTML을 렌더링합니다.
4. 에이전트가 OS 스풀러에 제출하거나 raw TCP/USB 포트를 엽니다.
5. SDK가 페이지에 성공 / 실패를 반환합니다.

일반적인 raw POS 작업은 3단계 HTML 렌더링을 건너뛰고 ESC/POS 또는 ZPL을 직접 보냅니다.

## 프로덕션에서 마주칠 실패 모드

| 증상 | 가능한 원인 | 확인할 곳 |
|---|---|---|
| 노트북에서는 되는데 배포 후 실패 | HTTP 사이트가 루프백 차단 | [Chrome Local Network Access](chrome-local-network-access.ko.md) |
| 연결은 되는데 인쇄 안 됨 | 잘못된 프린터 이름 / 오프라인 큐 | 프린터 조회; OS 스풀러 확인 |
| 화면과 레이아웃이 다름 | 다른 엔진 / 누락된 폰트 | 폰트 고정; 대상 OS에서 테스트 |
| 첫 작업만 느림, 이후 괜찮음 | 에이전트 콜드 스타트 / 인증서 프롬프트 | 로그인 시 사전 연결 |
| POS PC에서 간헐적 끊김 | 절전, 백신, 포트 충돌 | 에이전트를 서비스로 유지; 포트 예약 |

## localhost가 중요한 이유

로컬 브리지는 보통 `127.0.0.1`에서 수신합니다. 최신 Chromium 브라우저는 **Local Network Access** 규칙도 적용합니다. 공개/프로덕션 페이지는 `ws://127.0.0.1…`을 열기 전에 **HTTPS**가 필요한 경우가 많습니다. `http://localhost`에서의 개발은 다른 보안 컨텍스트이므로 "내 PC에서는 됐는데"가 흔합니다.

## 사일런트 프린트가 아닌 것

- PDF 생성 후 다운로드 (jsPDF, html2pdf…) — 유용하지만 인쇄는 아님
- 시스템 인쇄 대화상자 열기 (Print.js, `window.print()`)
- 서버 측 PDF 렌더링만 (Puppeteer) — **로컬** 프린터 경로 없음
- Electron 안에서만 "사일런트"인데 브라우저 빌드에서는 여전히 `window.print()` 사용

## 보안 기본선

로컬 에이전트를 권한 있는 소프트웨어처럼 다루세요.

- 벤더가 지원하면 인증 / 서명 채널 선호
- 에이전트 포트를 LAN이나 인터넷에 노출하지 않기
- 프린터와 템플릿 범위 제한; 신뢰할 수 없는 입력에서 "아무 URL 인쇄" 피하기
- 감사를 위해 job id → 사용자/스테이션 → 프린터 → 결과 로깅
