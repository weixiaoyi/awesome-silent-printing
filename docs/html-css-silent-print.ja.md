# HTML/CSS サイレント印刷

## チームがこれを望む理由

多くの業務 UI はすでに HTML/CSS です。サイレント印刷が同じテンプレートを再利用できれば、フロントエンドの速度を維持し、請求書ごとに ZPL/ESC/POS の第二スキルセットを維持する必要がありません。

## 2 つのレイアウトモデル

| モデル | メリット | デメリット |
|---|---|---|
| ローカル Chromium / エージェント経由 HTML/CSS | Web チームに馴染み；高い再現性 | ローカルエージェントが必要 |
| Raw ESC/POS / ZPL | 精密なデバイス制御 | 別スキルセット；ハードウェア固有 |

多くの製品は両方を混在：A4 ドキュメントは HTML、サーマル伝票は raw。

## ここでの「print CSS」の意味

ブラウザの `@media print` だけでは**サイレント経路にならない** — 依然 `window.print()` を通ります。ローカルエージェントでは通常：

1. 自己完結型 HTML 文字列（または URL）を組み立てる。
2. エージェントが必要とする CSS を含める（インライン、絶対 URL リンク、またはバンドル）。
3. SDK オプションで用紙サイズ / 余白 / プリンター名を渡す。
4. エージェントのエンジン（多くは Chromium）にページ分割とスプールを任せる。

### テンプレートチェックリスト

- [ ] 明示的なページサイズ（A4、100×150 mm、80 mm ロール等）
- [ ] 物理用紙に合う余白
- [ ] ワークステーションにインストール済みまたは埋め込みフォント
- [ ] バーコード / QR を SVG または高解像度画像（スキャンテスト）
- [ ] 最終行が切れないテーブル
- [ ] viewport 専用レイアウト（`100vh` トラップ）への依存なし

## 実践のヒント

- **印刷専用**スタイルシートを設計；アプリ全体の chrome CSS を盲目的に再利用しない。
- ラベルは `mm` / `in` 単位を優先；`px` だけでは DPI 間でずれる。
- Windows **と** Linux デスクの両方で中国語 / CJK フォントをテスト（両方サポートする場合）。
- テンプレート移行時はバッチ有効化前に 1 ジョブをプレビュー。
- 画像は小さく；巨大 PNG はバッチスループットを殺す。
- 正確なサーマルカッター / キャッシュドロワーには、raw 対応ブリッジで raw コマンドが依然必要な場合あり。

## 向いている用途

請求書、明細、梱包リスト、A4 レポート、HTML としてレンダリングする多くのラベルレイアウト。

## 向いていない用途（raw / ベンダー SDK を検討）

- ESC/POS のみを期待する超高速キッチンプリンター
- プリンターファームウェアで ZPL テンプレートに標準化された Zebra 端末群
- ベンダー raw 以外に使える Windows/macOS/Linux ドライバー経路がないデバイス
