# リモート / サーバー配信サイレント印刷

## ローカルブラウザ呼び出しでは足りない場合

- 梱包ステーションで業務 SPA を開く必要がない
- ジョブが中央 WMS/OMS で生成される
- 複数デスクが同じキューを消費する
- 夜勤が別拠点 UI で作られたジョブを印刷する

## 一般的なアーキテクチャ

```text
Business server
    → queue / webhook / websocket feed
    → desk print agent
    → local printer
```

ブラウザは設定（ステーション ↔ プリンターの紐付け）にのみ使われる場合があります。エージェントがジョブを継続的に pull または受信します。

### 2 つのトランスポートスタイル

| スタイル | 仕組み | 注意点 |
|---|---|---|
| クラウド中継（PrintNode 系） | サーバー API → ベンダークラウド → ローカルクライアント | アカウントセキュリティ、拠点ごとのマッピング |
| 自ホスト pull | エージェントがステーショントークンで API をポーリング | 認証、バックオフ、永続キュー |
| デザイナー系スタックの中継 | hiprint 系クライアント向け追加ホップ | 運用の複雑さ |

## 設計上の注意

- **エージェントを認証**；生の印刷ポートをインターネットに公開しない
- 可能ならジョブペイロードをローカル SDK 形状と同一に保つ（同じ HTML/PDF/raw）
- オフラインデスクは永続キューと poison ジョブ用デッドレター
- 運用用に `job id → station → printer → result` をログ
- テンプレートをバージョン管理；不良デプロイは履歴を二重印刷せずロールバック可能に
- ステーションごとにレート制限し、1 デスクが他を飢えさせない

## セキュリティチェックリスト

- [ ] ステーション認証情報がローテーション可能
- [ ] API への TLS
- [ ] ブラウザ機能は localhost のみにバインド；リモートチャネルはアウトバウンド
- [ ] 信頼できないジョブフィールドからの「任意 URL 印刷」なし
- [ ] どのステーションに誰がエンキューできるか監査

## 運用手順書（最低限）

1. ステーションオフライン → 最終ハートビート時刻と共にオンコール
2. プリンター用紙切れ → ステーション UI / LED（あれば）に表示
3. poison テンプレート → ジョブを隔離；テンプレート所有者にアラート
4. リプレイ → 明示的に失敗した id のみ
